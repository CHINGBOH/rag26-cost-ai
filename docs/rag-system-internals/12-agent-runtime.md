# Agent 运行机制与状态管理

## ReAct Agent 设计模式

RAG 智库系统的 Agent 采用 ReAct（Reasoning + Acting）设计模式。与简单的"提问→搜索→回答"不同，ReAct Agent 会先推理（Reasoning），想清楚要做什么；然后行动（Acting），调用工具执行；再观察（Observing）结果，判断是否足够；如果不够，重新推理，调整策略，再次行动。这个"推理-行动-观察"循环让 Agent 能处理复杂多步骤问题，例如先找费率→再找材料价格→再做计算，每一步的结果都影响下一步的决策。

## 工具调用决策机制

Agent 使用 LLM 作为"大脑"决定调用哪个工具。每次迭代，LLM 收到：当前用户问题、已有的检索结果摘要、可用的工具列表（含每个工具的描述和参数说明）、系统指令（角色定义、约束规则）。LLM 输出一个结构化的决策：CALL_TOOL（调用某个工具，附带参数）或 FINAL_ANSWER（给出最终答案）。这个决策过程完全透明，在前端的"运行沙盘"面板可以实时看到每次决策的推理过程。

## XState v5 状态机（Node.js 协调器）

Node.js 协调器（端口 3000）使用 XState v5 状态机管理每个会话的生命周期。状态转移路径：idle（空闲）→ querying（分析问题）→ thinking（LLM 推理）→ tool_calling（工具执行）→ observing（处理工具结果）→ answering（生成最终答案）→ done（完成）。每次状态转移都通过 WebSocket 实时推送到前端，让用户看到"系统正在查询"、"系统正在计算"等实时状态。XState v5 使用 createActor() 而非旧版的 interpret()，guard 条件必须是函数而非字符串。

## 共享状态（Channel）与版本控制

Agent 维护一个共享状态（Channel），记录整个推理过程中积累的信息：原始问题、查询分析结果、已检索到的段落列表、工具调用历史、中间计算结果、当前迭代计数。Channel 使用版本号追踪状态变化，每次工具调用后版本号递增。这种设计参考 LangGraph 的 Channel/State 概念，支持状态快照和恢复，即使工具调用失败也能从上一个稳定状态继续。前端展示的"共享状态"面板实时显示这个 Channel 的内容。

## 最大迭代次数与超时控制

Agent 的最大迭代次数默认为 3 次（图书馆模式固定），专业版可以调整（1-10）。每次迭代计为一次完整的"LLM 推理 + 工具调用 + 结果处理"循环。增加迭代次数可以处理更复杂的问题，但也会增加响应时间。每次工具调用有独立超时（数据库查询 30 秒，LLM 生成 120 秒），超时后 Agent 记录错误继续下一步，不会无限等待。整个 Agent 运行也有全局超时（默认 300 秒），防止无限循环。

## Agent 运行日志与轨迹

每次 Agent 运行都会保存完整日志到 agent_runs 表（PostgreSQL），包括：运行 ID、用户问题、工具调用序列（每个工具的参数和返回值）、最终答案、运行时长、置信度分数。这些日志用于：系统优化（找出哪些问题工具选择不当）、盲点分析（find_knowledge_gaps 工具读取这些日志分析知识库薄弱点）、审计溯源（每个答案都能追溯到具体工具调用过程）。前端"Server Traces"面板展示实时运行日志。
